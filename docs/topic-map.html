JD bullets → where they live

JD 1 + 3 · CircleCI

Stable, fast, scalable pipelines

  • .circleci/config.yml → commands: 6 reusable commands (setup_bazel, restore/save_bazel_cache, auth_gar, install_crane, notify_failure)
  • orbs: circleci/gcp-cli (OIDC), circleci/slack
  • workflows: pr · main · nightly · release · hotfix, selected by pipeline parameters
  • scripts/*.sh: every job body is a script
Say thisNothing is copy-pasted, the expensive work is cached — read-write on main, read-only on PRs so a PR can't poison it — and every job body is a script I can run locally, which is also what makes it portable off CircleCI.
JD 2 · Bazel ecosystem

Graph, caching, RBE, troubleshooting

  • MODULE.bazel + .lock: bzlmod, hermetic CPython, base image by digest, lock committed
  • .bazelrc: --config=rbe (executor, BES, jobs=100, platforms), remotecache / remotecache_ro
  • --incompatible_strict_action_env: the "why does CI never cache" fix
  • libs/version: codegen inside the graph, so a version bump has a visible blast radius
  • scripts/ci-build.sh: a bazel query guard — no service may depend on //tools/…
Say thisPython-only for size, but the mechanics are language-agnostic: adding Go is a bazel_dep plus a go_image macro next to py_image.bzl. The manifest, the CI config and the chart don't change — that separation is the design.
JD 4 · Release modes

Manifest + version files drive everything

  • release/manifest.yaml: images, repos, versions, smoke flag, charts
  • release/version.txt: one version, feeding both the build and the tags
  • tools/release/release.py: nightly / release / hotfix, --only, --registry, --dry-run, JSON report
  • release_test.py: the tag rules are unit tested — no registry needed
Say thisCI doesn't know which services exist — adding one is a manifest PR, not a CI PR. Every mode publishes at least one immutable tag; floating tags like latest are only ever additional, so a rollback is always "pin the immutable tag".
JD 5 · Artifacts + registries

GAR / JFrog, crane, hotfix delivery

  • tools/bazel/py_image.bzl: oci_image + oci_load + oci_push, reproducible layers
  • release.py → publish(): crane push / tag / digest, docker fallback
  • scripts/release.sh: helm package + helm push (OCI chart) next to the images
  • auth_gar: Workload Identity Federation — no long-lived JSON key
  • --registry override: a hotfix goes straight into the customer's registry
Say thiscrane talks to the registry directly — no docker daemon in CI — and re-tagging is a metadata call instead of a layer upload. crane copy is how you promote between registries without ever pulling.
JD 6 · Build + smoke validation

What gets checked, and when

  • bazel test //…: 4 hermetic tests, no docker or cluster
  • tests/smoke/smoke_test.py: health · deployed version == released version · one real endpoint
  • tags = ["manual","external"]: never runs (or caches) in the hermetic suite
  • deploy_and_smoke: smoke after helm upgrade; when: on_fail → helm rollback
Say thisThe assertion that earns its keep is comparing /version with the tag we just published — a rollout can report success while the cluster still serves the old image.
JD 7 + qualifications

Rollout, Python, Bash, dependencies

  • py_image.bzl: platform team owns one macro — changing the base image for every service is a one-line diff
  • third_party/python: requirements.in → hashed lock, one version repo-wide, CI test fails on drift
  • scripts/*.sh: set -euo pipefail, ${VAR:?msg}, --dry-run on anything that mutates
  • docs/: the rollout is documented, not tribal knowledge
Say thisA version number never appears in a BUILD file — deps are written as requirement("pyyaml") and pinned once, in one lock, for the whole monorepo.

Questions you should expect

Our CI cache never hits. Where do you look?

In order: is the action environment leaking (--incompatible_strict_action_env); are the toolchains hermetic or is a system python sneaking in; are outputs reproducible — timestamps in tars and image layers are the usual culprit, which is why the macro sets portable_mtime; diff two invocations with --execution_log_compact_file; and check PRs aren't writing junk into the shared cache (they're read-only here on purpose).

Nightly vs release — how do you avoid two copies of the pipeline?

Pipeline parameters. A scheduled pipeline sets run_nightly=true, which selects the nightly workflow and reuses the same build / publish / deploy jobs with different parameters. The only real difference is the release mode, which is a flag to the release tool.

latest — yes or no?

Publish it, never deploy it. It's a convenience pointer for humans; deployments always reference an immutable tag or a digest, otherwise rollback is undefined.

A build works locally and fails on RBE. First move?

bazel aquery the failing action and read its declared inputs. Nine times out of ten something is used but not declared, and the local sandbox was lenient about it.

A customer needs a fix on 1.4.0 but main is on 1.6.

Branch from the release tag, cherry-pick, run the hotfix pipeline for that one component with --registry <customer registry>. It publishes 1.4.0-hotfix.1, never touches latest, and the JSON release report — with digests — goes on the support ticket.

How would you make this pipeline faster?

Measure first, then: fail cheap checks first, cache the expensive layer (Bazel remote cache), stop redoing work across jobs (persist_to_workspace), and only then add parallelism. I deliberately did not shard tests — Bazel already skips unchanged ones, so sharding mostly buys container startup cost. Knowing when not to shard is part of the answer.

Honest limitations of the demo

  • Python only. Go and Rust would be added the same way, but they aren't here.
  • The RBE and remote-cache endpoints in .bazelrc are illustrative — the flags and the platform definition are real, the backends aren't provisioned.
  • Images use python:3.11-slim, not distroless, because the rules_python launcher starts with #!/usr/bin/env python3. Going distroless means changing the bootstrap strategy.
  • The demo registry is a local registry:2, and smoke reaches the cluster over a NodePort — in production that's an internal load balancer or Ingress.
